# Введение

Настоящая курсовая работа посвящена переносу и развитию автоматизированной
системы образовательного учреждения дистанционного обучения (АС ОУДО),
изначально спроектированной в Microsoft Access, на современный кроссплатформенный
стек: реляционную СУБД PostgreSQL и графический интерфейс на базе фреймворка
Qt 5 (PyQt5).

**Цель проекта** — спроектировать и реализовать клиент-серверную информационную
систему, обеспечивающую автоматизацию основных процессов образовательного
учреждения дистанционного обучения: управление справочниками студентов,
преподавателей и сотрудников, ведение учебных планов и курсов, регистрацию
договоров, выдачу заданий, выставление оценок и формирование отчётности.

**Задачи проекта:**

- получение навыков информационного и датологического проектирования
  реляционных баз данных, в том числе нормализации до НФБК и определения
  ограничений целостности;
- освоение СУБД PostgreSQL версии 13 и выше, утилиты `psql`, графического
  клиента pgAdmin, языка SQL в его расширенном (диалект PostgreSQL) виде;
- получение навыков создания настольных приложений к базам данных с
  использованием фреймворка Qt 5 (PyQt5), стандартной библиотеки Python 3.10+
  и драйвера `psycopg2`;
- получение навыков моделирования предметной области в графических нотациях
  DFD, IDEF0, ERD;
- получение навыков оформления документации: РПЗ по ГОСТ 7.32, технического
  задания по ГОСТ 19.201, программы и методики испытаний по ГОСТ 19.301;
- освоение приёмов оптимизации запросов: построение индексов, анализ плана
  выполнения через `EXPLAIN ANALYZE`.

В результате выполнения работы построена работающая система, состоящая из
схемы базы данных в PostgreSQL (11 таблиц, 5 пользовательских ENUM-типов,
7 представлений, 17 индексов, в том числе 5 функциональных по
`LOWER(...)`, базовый и «нагрузочный» пакеты тестовых данных), кроссплатформенного
клиентского приложения на PyQt5 (более 20 экранных форм, в том числе
master-detail и графические отчёты на Qt Charts, разделённых по трём
ролям пользователей — администратор, преподаватель, студент) и комплекта
проектной документации.

# 3. Анализ и описание предметной области

Объект автоматизации — учебная деятельность образовательного учреждения,
реализующего программы дистанционного обучения. На уровне предметной области
действуют три категории пользователей и шесть основных групп информационных
объектов.

**Действующие лица.**

- *Сотрудник (администратор).* Сотрудник учебной части, управляющий
  справочниками: вносит дисциплины, создаёт курсы, регистрирует студентов
  и преподавателей, заключает договоры, контролирует наполненность групп.
- *Преподаватель.* Лицо, ведущее закреплённые за ним курсы. Готовит
  задания и варианты, проверяет работы, выставляет оценки, формирует
  отчёты по успеваемости группы.
- *Студент.* Лицо, проходящее обучение на одном или нескольких курсах.
  Просматривает каталог собственных курсов, видит свои оценки, формирует
  итог по 100-балльной системе.

**Информационные объекты.**

- *Дисциплина.* Учебный предмет с заданным числом часов и описанием
  (математика, физика, базы данных и т. п.).
- *Курс.* Конкретная реализация дисциплины в определённом учебном году с
  закреплённым преподавателем.
- *Запись на курс.* Связующая сущность между студентом и курсом со статусом
  «активна / неактивна».
- *Договор.* Юридический документ. Договор об обучении заключается между
  сотрудником и студентом, трудовой договор — между сотрудником и
  преподавателем.
- *Задание.* Учебная работа в рамках курса (домашнее задание, лабораторная,
  тест, контрольная, эссе, курсовая, экзамен) со сроком сдачи и максимальным
  баллом.
- *Вариант задания.* Индивидуальный набор условий для конкретного задания.
- *Оценка.* Результат проверки задания у конкретного студента (целое число
  от 0 до 100).

# 4. Ограничения предметной области

1. Каждый пользователь имеет ровно одну роль: администратор, преподаватель
   или студент.
2. Логин пользователя уникален в пределах системы; пароль хранится только
   в виде bcrypt-хеша.
3. Запись `students` / `teachers` / `employees` всегда связана с одной
   учётной записью `users` (отношение 1:1). При удалении учётки запись в
   профильной таблице удаляется каскадно.
4. Студент может быть в одном из четырёх состояний: «учится»,
   «академический отпуск», «отчислен», «окончил». Переходы между
   состояниями выполняются только администратором.
5. Курс читается одним преподавателем и относится строго к одной
   дисциплине. Дата окончания курса должна быть строго позже даты начала.
6. Студент может быть записан на курс не более одного раза (отношение
   M:N с уникальной парой `(student_id, course_id)`).
7. Договор связан ровно с одной стороной — студентом или преподавателем —
   в зависимости от типа: «об обучении» или «трудовой».
8. Задание принадлежит одному курсу. У задания может быть произвольное
   число вариантов с уникальным номером.
9. Оценка ставится конкретному студенту за конкретное задание; пара
   `(student_id, task_id)` уникальна.
10. Балл оценки — целое число в диапазоне 0–100; за пределами диапазона
    база отвергает запись (CHECK-ограничение).

Перечисленные ограничения реализованы средствами PostgreSQL: внешние ключи
(`REFERENCES ... ON DELETE …`), пользовательские перечислимые типы
(`CREATE TYPE … AS ENUM`), уникальные индексы (`UNIQUE`),
CHECK-ограничения для диапазонных проверок (балл 0–100, число часов
дисциплины, разница дат курса) и NOT NULL для обязательных полей. Полная
сводка средств целостности приведена в §12 «Датологическая модель».

# 5. Описание входных документов и сообщений

На вход системы поступают:

- сведения о вновь зачисляемых студентах (ФИО, дата зачисления);
- сведения о принимаемых преподавателях и сотрудниках (ФИО, должность,
  специализация / уровень доступа);
- учебные планы — справочник дисциплин и план курсов на учебный год;
- заявки на запись на курс — пары «студент—курс» с датой подачи;
- данные договоров — подписанные образцы документооборота;
- учебные задания и варианты, формируемые преподавателями;
- результаты проверки работ — баллы оценок;
- учётные данные пользователей при входе (логин и пароль).

# 6. Описание выходных документов и сообщений

Система формирует следующие выходные документы:

- список курсов с указанием дисциплины, преподавателя, дат и числа
  активных студентов;
- сводку по записи студентов на курсы — статус, число активных и
  неактивных записей, хронологию;
- список преподавателей с привязкой к курсам;
- средний балл по каждому курсу;
- средний балл по каждому студенту;
- детализированный отчёт «Баллы студента» с разбивкой по курсам и
  заданиям;
- отчёт по 100-балльной системе с учётом весов заданий;
- **графические аналитические отчёты** (см. §15.6): столбчатая диаграмма
  «Средний балл по курсу (топ-12)» и круговая диаграмма «Распределение
  студентов по статусам» — оба построены средствами Qt Charts;
- **печатные карточки одной сущности** (см. §15.7): «Карточка студента»
  с реквизитами и подчинённой таблицей оценок;
- системные сообщения: подтверждения операций (`QMessageBox.information`),
  предупреждения о валидации (`QMessageBox.warning`), сообщения об
  ошибках БД (`QMessageBox.critical`).

Все табличные отчёты и карточки выводятся в окно `QPrintPreviewDialog`
и могут быть сохранены в формате PDF средствами Qt без дополнительных
библиотек. Графические отчёты отображаются прямо в окне Qt Charts с
анимацией.

# 8. Модель предметной области в нотации DFD

Диаграмма потоков данных (DFD) описывает движение информации между
внешними сущностями, процессами и хранилищами. На контекстной диаграмме
отображаются три внешние сущности — сотрудник, преподаватель и студент,
а также пять процессов первого уровня декомпозиции и пять групп
хранилищ. Полная диаграмма приведена на листе 2 графической части.

## 8.1 Графическая диаграмма

![](graphics/02_dfd.png){ width=16cm }

## 8.2 Описание модели

**Внешние сущности:** сотрудник, преподаватель, студент.

**Процессы первого уровня декомпозиции (DFD-1):**

1. Аутентификация. Принимает логин и пароль, обращается к хранилищу
   учётных записей `users`, возвращает идентификатор сессии и роль.
2. Управление справочниками. Принимает CRUD-команды от сотрудника, читает
   и пишет справочники студентов, преподавателей, сотрудников, дисциплин и
   курсов.
3. Учёт договоров и записей на курс. Отдельный процесс, поскольку охватывает
   юридически значимый документооборот.
4. Ведение заданий и оценок. Доступен преподавателю; читает и пишет
   `tasks`, `variants`, `grades`.
5. Формирование отчётов и печать. Принимает запрос отчёта от любой роли,
   читает данные из всех справочников, формирует HTML-документ и передаёт
   в `QPrintPreviewDialog`.

**Хранилища данных:** D1 `users`; D2 `students` / `teachers` / `employees`;
D3 `disciplines` / `courses`; D4 `contracts` / `enrollments`;
D5 `tasks` / `variants` / `grades`.

# 9. Модель предметной области в нотации IDEF0

Функциональная модель IDEF0 фокусируется на бизнес-функциях системы и
управляющих воздействиях. Контекстная диаграмма A-0 показывает АС ОУДО
как «чёрный ящик» с входами, управлением, механизмами и выходами;
декомпозиция A0 разделяет функцию на четыре блока: управление
справочниками, ведение договоров и записей, ведение оценок и
формирование отчётности. Полная диаграмма приведена на листе 3
графической части.

## 9.1 Графическая диаграмма

![](graphics/03_idef0.png){ width=16cm }

*Рисунок 25 — Функциональная модель IDEF0.*

## 9.2 Описание модели

**Контекстная диаграмма A-0 «Управление учебным процессом АС ОУДО».**

- Входы: заявления студентов, учебные планы и образовательные стандарты,
  результаты выполнения заданий.
- Управление: образовательные стандарты, локальные нормативные акты,
  положение о промежуточной аттестации, регламент отчётности.
- Механизмы: сотрудник, преподаватель, АС ОУДО (БД и UI).
- Выходы: заключённые договоры, отчёт об успеваемости, аналитика для
  администрации.

**Декомпозиция A0:**

- A1. Управлять справочниками (сотрудник + АС).
- A2. Вести договоры и записи на курс (сотрудник + АС). Получает на вход
  справочники из A1.
- A3. Вести задания и оценки (преподаватель + АС). Получает на вход записи
  из A2.
- A4. Формировать отчётность (АС). Получает на вход массив оценок из A3
  и справочники из A1, выдаёт отчёты.

# 10. Инфологическая модель предметной области

Инфологическая (ER) модель формализует объекты предметной области и
связи между ними без привязки к конкретной СУБД. Модель содержит
11 сущностей (учётные записи, профили пользователей трёх ролей,
дисциплины, курсы, записи на курс, договоры, задания, варианты, оценки)
и связи с указанием кардинальности. Полная диаграмма приведена на
листе 4 графической части.

## 10.1 Графическая диаграмма

![](graphics/04_er_model.png){ width=16cm }

*Рисунок 26 — Инфологическая (ER) модель.*

## 10.2 Спецификация инфологической модели

### 10.2.1 Атрибуты

- **Идентификаторы.** id (счётчик) для каждой сущности — уникальный
  суррогатный ключ.
- **Учётная запись.** login (короткий текст), password_hash (текст 60–72),
  role (короткий текст из набора), created_at (дата-время).
- **Профиль человека.** full_name (текст), position (текст),
  specialization / access_level (текст из набора), enrollment_date (дата),
  status (текст из набора).
- **Учебный план.** name (текст), hours (целое), description (длинный
  текст), start_date / end_date (дата).
- **Учебная активность.** title (текст), description (длинный текст),
  type (текст из набора), deadline (дата-время), max_score (целое),
  number (целое), score (целое 0–100), graded_at (дата-время).
- **Запись и договор.** enrollment_date / contract_date (дата),
  contract_type (текст из набора), is_active (логический).

### 10.2.2 Сущности

- USERS, EMPLOYEES, TEACHERS, STUDENTS — пользователи и их профили.
- DISCIPLINES, COURSES — учебные ресурсы.
- ENROLLMENTS, CONTRACTS — фиксация связи людей с курсами и юридического
  документооборота.
- TASKS, VARIANTS, GRADES — учебная активность и её оценивание.

| Получает       | 1:M  | STUDENTS — GRADES     | FK `grades.student_id`, UNIQUE (student_id, task_id)                     |

# 11. Выбор СУБД

В качестве реляционной СУБД выбрана **PostgreSQL 17** (минимально
поддерживаемая совместимая версия — 13). Контейнер `postgres:17-alpine`
поднимается через `docker-compose.yml`, сервис слушает порт 5433 на
хосте и 5432 внутри контейнера. Решение продиктовано следующими
факторами.

1. PostgreSQL — полностью бесплатная СУБД с открытым исходным кодом
   (лицензия PostgreSQL License, эквивалентна BSD/MIT), что снимает
   юридические ограничения на распространение.
2. Поддерживает все требуемые конструкции: ограничения целостности
   (PRIMARY KEY, UNIQUE, NOT NULL, CHECK, REFERENCES), сложные SQL-запросы
   (JOIN, агрегаты, оконные функции, общие табличные выражения, LATERAL),
   представления и индексы.
3. Расширение `pgcrypto` позволяет рассчитывать bcrypt-хеши паролей прямо
   в `INSERT` (`crypt(password, gen_salt('bf', 10))`), причём результат
   совместим с проверкой через библиотеку `bcrypt` в Python.
4. Команда `EXPLAIN (ANALYZE, BUFFERS)` даёт подробный план выполнения
   запроса, что позволяет наглядно продемонстрировать эффект от добавления
   индексов (см. §17).
5. Кроссплатформенность: PostgreSQL работает в Linux, macOS и Windows,
   что соответствует требованию ТЗ.

В качестве клиентского приложения используется фреймворк **Qt 5 в
биндингах PyQt5** на языке Python 3.10. Драйвер базы — `psycopg2-binary`,
работа с пулом соединений — через `psycopg2.pool.SimpleConnectionPool`.
Графические отчёты построены на модуле **PyQtChart** (биндинги к Qt Charts),
который добавляется в `requirements.txt` отдельно от ядра PyQt5. Качество
отрисовки виджетов и диаграмм на macOS, Linux и Windows одинаково; для
запуска не требуется ничего, кроме интерпретатора Python и пакетов из
`requirements.txt`.

## 12.3 Пользовательские перечислимые типы (ENUM)

Поля с фиксированным набором значений реализованы через
`CREATE TYPE … AS ENUM` — это идиоматичный подход для PostgreSQL, более
выразительный и компактный, чем хранение строковой константы с
`CHECK IN (...)`. ENUM проверяет значения на этапе `INSERT`/`UPDATE`
без отдельного CHECK-выражения, занимает 4 байта вместо переменной
длины VARCHAR и автоматически вписывается в `pg_type` для целей
интроспекции.

В схеме определены пять ENUM-типов:

- `user_role` — `('admin', 'teacher', 'student')`, поле `users.role`;
- `access_level` — `('standard', 'extended', 'super')`, поле
  `employees.access_level`;
- `student_status` — `('studying', 'academic_leave', 'expelled',
  'graduated')`, поле `students.status`;
- `task_type` — `('homework', 'lab', 'test', 'control', 'essay',
  'coursework', 'exam')`, поле `tasks.type`;
- `contract_type` — `('education', 'employment')`, поле
  `contracts.contract_type`.

CHECK-ограничения сохранены только для диапазонных проверок: количество
часов дисциплины, диапазон оценки 0–100, корректность дат курса
(`end_date > start_date`), полиморфная связность договоров.

## 12.4 Индексы и функциональные индексы

В файле `sql/02_indexes.sql` определены 17 индексов трёх категорий:

1. **B-tree по уникальным полям** для авторизации: `ix_users_login`.
2. **B-tree по часто сортируемым полям** для CRUD-таблиц:
   `ix_employees_full_name`, `ix_teachers_full_name`,
   `ix_students_full_name`.
3. **FK-индексы**, которые PostgreSQL не создаёт автоматически:
   `ix_courses_teacher_id`, `ix_courses_discipline_id`,
   `ix_enrollments_course_id`, `ix_tasks_course_id`, `ix_variants_task_id`,
   `ix_contracts_employee_id`, `ix_contracts_student_id`,
   `ix_contracts_teacher_id`.
4. **Функциональные индексы по `LOWER(...)`** для регистронезависимого
   поиска через `ILIKE` в CRUD-формах: `ix_employees_fn_lower`,
   `ix_teachers_fn_lower`, `ix_students_fn_lower`,
   `ix_disciplines_name_lower`, `ix_courses_name_lower`. Они позволяют
   планировщику применять Index Scan для запросов вида
   `LOWER(field) LIKE 'буква%'` — что особенно заметно на больших
   объёмах (см. §17).
5. **Составной индекс по двум колонкам** `ix_grades_student_task`
   `(student_id, task_id)` — для агрегатных отчётов «Баллы студента»
   и «Средний балл».

**Уровень нормализации.** Схема приведена к нормальной форме Бойса—Кодда
(НФБК): каждая таблица имеет один ключ-кандидат, нетривиальные функциональные
зависимости устраняются за счёт суррогатных ключей, многозначные
зависимости отсутствуют.

## 13.2 Описание схемы работы

Работа системы начинается с окна **«Авторизация»** (рисунок 2). В нём

Кнопка «Выйти из приложения» закрывает окно и завершает процесс. При

с текстом «Неверный логин или пароль», поле пароля очищается.

### 13.2.1 Меню сотрудника

В меню десять кнопок: семь — для управления справочниками («Студенты»,
«Преподаватели», «Сотрудники», «Дисциплины», «Курсы», «Запись на курс»,
«Договоры»), три — для отчётов («Курсы», «Запись», «Преподаватели»).
Снизу — две системные кнопки «Выйти из аккаунта» и «Выйти из приложения».

Каждая CRUD-форма устроена одинаково (родительский класс `CrudView`):
- сверху строка поиска — фильтр по подстроке в основных полях (через
  `ILIKE` с использованием функциональных индексов, см. §12.4);
- слева таблица `QTableWidget` со списком записей;
- справа форма ввода полей; при выделении строки она автоматически
  заполняет форму;
- внизу шесть-семь кнопок: «Добавить», «Изменить», «Удалить», «Очистить»,
  «Печать», опционально «Карточка» (печать одной сущности, см. §15.7),
  «Назад».

Форма «Курсы» дополнительно реализует паттерн **master-detail**: под
основной таблицей курсов размещена подчинённая таблица «Задания курса»,
которая автоматически обновляется при изменении выделения в основной
таблице (хук `on_row_selected` в `CrudView`). Список заданий выбранного
курса показывается без дополнительной навигации — для удобства проверки
наполненности курса учебными материалами.

Действия сопровождаются диалогами `QMessageBox`: подтверждение успешной
вставки, запрос подтверждения удаления, предупреждение при пустых
обязательных полях, критическое сообщение при ошибке БД.

### 13.2.2 Меню преподавателя

В меню шесть кнопок: «Задания», «Варианты», «Оценки», три отчёта
(«100-балльная система», «Средний балл», «Баллы студента»). CRUD-формы
работают аналогично админским; отчёты открывают окна с табличным
представлением, кнопками «Обновить» и «Печать».

### 13.2.3 Меню студента

Доступно только три отчёта в режиме «только чтение»: «Мои курсы»,
«Мои оценки», «100-балльная система». Идентификатор студента
автоматически передаётся в SQL-запросы из объекта сессии, поэтому студент
видит только свои данные.

## 16.2 Описание

Граф диалога описывает все возможные переходы между экранами с указанием
условий. Из окна авторизации возможно три перехода — в меню одной из
ролей. Внутри каждой CRUD-формы две метастабильности (`Listing` и
`Editing`); переход `Listing → Editing` происходит при выборе строки в
таблице, обратный — при нажатии «Очистить». Удаление приводит к
возврату в `Listing` после диалога подтверждения. Ошибки уровня БД
держат пользователя в текущем состоянии и показывают `QMessageBox.critical`.

Кнопка «Выйти из аккаунта» в любом меню возвращает к окну авторизации
со сбросом сессии. «Выйти из приложения» — финальный переход в стоп-узел.

# 17. Оптимизация запроса

Для демонстрации эффекта индекса важно использовать «продакшен-объём»
данных. Базовый seed (`sql/04_seed.sql`) содержит 30 студентов, 60
заданий и около 337 оценок — на таких объёмах планировщик
часто помещает всю таблицу в буфер и выбирает Seq Scan просто потому,
что это дешевле, чем чтение индекса. Чтобы получить осмысленные
результаты `EXPLAIN ANALYZE`, в проект добавлен «нагрузочный» скрипт
`sql/06_seed_bulk.sql`, который дополнительно вставляет:

- 2 000 студентов (логины `bulk_student_0001` … `bulk_student_2000`);
- 200 курсов (`Bulk-курс №001` … `Bulk-курс №200`);
- 10 000 записей на курсы (по 5 на студента);
- 2 000 заданий (по 10 на bulk-курс);
- ≈ 70 000 оценок (с вероятностью 70% на каждую пару «запись × задание»).

Bulk-seed запускается командой `make db-seed-bulk` и идемпотентен
(на каждом запуске использует `ON CONFLICT DO NOTHING`). Скрипт
оптимизации `sql/05_optimize.sql` рассчитан именно на эти объёмы.

## 17.1 Кандидат на оптимизацию

В качестве кандидата выбран запрос «регистронезависимый поиск студентов
по подстроке ФИО» — типовая операция CRUD-формы «Студенты»:

```sql
SELECT id, full_name, status, enrollment_date
FROM   students
WHERE  LOWER(full_name) LIKE LOWER('Bulk-студент №15%')
ORDER  BY full_name;
```

Запрос отбирает префиксное совпадение и возвращает около 100 строк из
2 030 студентов — высокая селективность, на которой индекс даёт
заметный эффект.

## 17.2 До оптимизации

После удаления функционального индекса:

```sql
DROP INDEX IF EXISTS ix_students_fn_lower;
DROP INDEX IF EXISTS ix_students_full_name;
ANALYZE students;
```

`EXPLAIN (ANALYZE, BUFFERS, COSTS, TIMING)` показывает план с полным
последовательным сканированием:

```
Sort  (cost=50.46..50.47 rows=1 width=40) (actual ... rows=100)
  Sort Key: full_name
  Buffers: shared hit=20
  ->  Seq Scan on students  (cost=0.00..50.45 rows=1 width=40)
                            (actual rows=100 loops=1)
        Filter: (lower((full_name)::text) ~~ 'bulk-студент №15%'::text)
        Rows Removed by Filter: 1930
        Buffers: shared hit=20
Planning Time: 0.107 ms
Execution Time: 0.304 ms
```

Ключевые показатели плана *до оптимизации*:

- стоимость по оценке планировщика — **50.46 cost**;
- тип сканирования — `Seq Scan` по всем 2 030 строкам;
- отброшено фильтром — 1 930 строк (95% объёма);
- число прочитанных буферов (shared hit) — 20;
- фактическое время выполнения — **0.304 мс**.

## 17.3 После оптимизации

Создаётся функциональный индекс по `LOWER(full_name)`:

```sql
CREATE INDEX ix_students_fn_lower ON students (LOWER(full_name));
ANALYZE students;
```

Повторный `EXPLAIN ANALYZE` показывает Index Scan по новому индексу:

```
Sort  (cost=26.95..27.20 rows=103 width=32) (actual ... rows=100)
  Sort Key: full_name
  Buffers: shared hit=2 read=2
  ->  Index Scan using ix_students_fn_lower on students
              (cost=0.28..23.50 rows=103 width=32)
              (actual rows=100 loops=1)
        Index Cond: ((lower(...) >= 'bulk-студент №15')
                 AND (lower(...) < 'bulk-студент №16'))
        Filter: (lower(...) ~~ 'bulk-студент №15%'::text)
        Buffers: shared hit=2 read=2
Planning Time: 0.077 ms
Execution Time: 0.078 ms
```

Изменения:

- стоимость снизилась с **50.46 до 27.20 cost — почти в 1,86 раза**;
- `Seq Scan` заменён на `Index Scan`: планировщик трактует
  `LOWER(...) LIKE 'X%'` как диапазонное условие
  `LOWER(...) >= 'X' AND LOWER(...) < 'Y'`, и индекс используется
  напрямую;
- предполагаемое число строк (`rows=103`) точно совпадает с фактом
  (`rows=100`) — статистика после `ANALYZE` стала достоверной;
- число прочитанных буферов снизилось с 20 до 4 (×5);
- фактическое время выполнения уменьшилось с 0.304 до 0.078 мс — почти
  в **4 раза**.

|---------------------|-------------|------------|-------|

## 17.5 Замечание о подстрочном поиске

Для условий вида `LOWER(field) LIKE '%X%'` (подстрока с ведущим
символом-джокером) функциональный B-tree-индекс **не применим**:
индексы по этой структуре поддерживают только диапазонный поиск, и
PostgreSQL обоснованно выберет Seq Scan. Если в будущем потребуется
ускорить и подстрочный поиск, необходимо подключить расширение
`pg_trgm` и построить GIN-индекс:

```sql
CREATE EXTENSION pg_trgm;
CREATE INDEX ix_students_fn_trgm ON students USING gin (LOWER(full_name) gin_trgm_ops);
```

В рамках курсовой работы это вынесено в перечень потенциальных
расширений и не реализовано.

Полный вывод `EXPLAIN ANALYZE` (включая блоки до/после оптимизации
и шаг 5 — префиксный поиск) сохраняется в файле
`build/explain_bulk_output.txt` после прогона цели
`make db-explain-bulk`.

# 18. Развёртывание системы

Окружение для разработки и эксплуатации описано в файле
`docker-compose.yml` корня проекта и автоматизировано через `Makefile`.

**Стек развёртывания:**

- PostgreSQL 17 (`postgres:17-alpine`) в Docker-контейнере с пробросом
  порта 5433 на хост (внутри контейнера — стандартный 5432);
- персистентный том `ac_oudo_pgdata` для каталога данных PostgreSQL;
- Python 3.10+ с виртуальным окружением `.venv` (создаётся через
  `make venv`);
- зависимости фиксируются в `requirements.txt`: `PyQt5`, `PyQtChart`,
  `psycopg2-binary`, `bcrypt`, `python-dotenv`.

**Сценарии Makefile:**

- `make bootstrap` — поднять контейнер БД, установить зависимости, накатить
  миграции (`01_schema.sql` → `04_seed.sql`);
- `make db-seed-bulk` — дозалить нагрузочный пакет (`06_seed_bulk.sql`);
- `make db-explain-bulk` — прогнать сценарий оптимизации (`05_optimize.sql`)
  и сохранить вывод в `build/explain_bulk_output.txt`;
- `make run` — запустить приложение под текущим виртуальным окружением;
- `make db-reset` — снести том с данными и пересоздать БД с нуля;
- `make rpz` — пересобрать `build/Воробьёв_РПЗ.docx` через pandoc.

**Настройки подключения** хранятся в `.env` (шаблон — `.env.example`):
строка `DATABASE_URL=postgresql://postgres:postgres@localhost:5433/ac_oudo`.
Приложение через `python-dotenv` подхватывает её при старте; для
production-развёртывания достаточно подменить переменную окружения
без перекомпиляции кода.

**Apple Silicon.** Makefile содержит автоматическое определение
архитектуры через `sysctl hw.optional.arm64` и принудительно использует
`arch -arm64` для всех Python-вызовов — иначе universal-бинарь Python
может выбрать x86_64-режим, и arm64-wheel'ы PyQt5/PyQtChart не
загрузятся.
